# Модерация жителей — дизайн

**Дата:** 2026-06-02
**Проект:** CleanCity (Чистый Город)
**Статус:** одобрен к написанию плана реализации

## Проблема

Сейчас в системе нет штатного способа ограничить жителя (`RESIDENT`), который
злоупотребляет подачей жалоб (спам, ложные обращения, недопустимый контент).
Механизм заморозки (`/admin/users/{id}/freeze`) намеренно отклоняет резидентов —
он предназначен для управления командой сотрудников. Единственные сдерживающие
факторы для жителей — автоблокировка при брутфорсе (`locked_until`) и требование
подтверждённого email.

## Цель

Дать сотрудникам инструмент модерации жителей с **человеком в петле** и полным
аудит-следом. Система только подсказывает (флаг), решение всегда принимает
сотрудник. Градуированный ответ: сигнал → предупреждение → бан, плюс возможность
немедленного бана за грубое разовое нарушение.

## Не-цели (YAGNI)

- Никаких авто-банов и авто-предупреждений — система ничего не делает сама, только
  подсвечивает.
- Отдельная страница/раздел «Модерация» не создаётся — действия живут на детали
  жалобы.
- Поле «тип причины отклонения» (enum) не вводится — причина остаётся свободным
  текстом (`status_changes.comment`, уже `NOT NULL`).
- Модерация контента до публикации (премодерация) — вне scope.

## Контекст из текущего кода (факты)

- Статусы жалобы: `NEW`, `IN_PROGRESS`, `RESOLVED`, `REJECTED`, `DUPLICATE`.
  `DUPLICATE` — **отдельный** статус, не `REJECTED`. Значит счёт по `REJECTED`
  автоматически не штрафует за дубликаты.
- При отклонении (`REJECTED`) причина **обязательна** — это `comment` в
  `status_changes` (`NOT NULL`).
- Логин уже отклоняет неактивных: `if (!user.isActive) throw InvalidCredentialsException()`,
  и заблокированных по `locked_until`.
- Заморозка сотрудника = `users.setActive(false)` + `revokeAllUserRefreshTokens(...)`
  + запись в `audit_log`. Бан жителя переиспользует ту же механику.
- `notifications.kind` ограничен CHECK-констрейнтом (`COMPLAINT_STATUS`,
  `ANNOUNCEMENT`) + парный CHECK на `complaint_id`/`announcement_id`.
- `AuditAction` — enum в `database/tables/AuditLog.kt`.
- Веб-админка: раздел «Жалобы» с детальным просмотром жалобы.

## Решение

### Две дорожки

1. **Авто-флаг (систематика).** Житель подсвечивается «на проверку», когда у него
   накопилось **≥ 3** жалоб `REJECTED` с момента последнего предупреждения
   (`DUPLICATE` не считается). Это только подсветка — никаких действий.
2. **Ручное действие (в любой момент).** Сотрудник может предупредить или сразу
   забанить автора прямо на жалобе — даже за одну жалобу, если контент
   недопустим (18+, оскорбления и т.п.).

### Лестница действий (всё решает человек)

1. **Флаг** — система подсвечивает, никого не наказывает.
2. **Предупреждение** — сотрудник шлёт жителю уведомление с обязательной причиной
   («нарушаете правила, при повторении — бан навсегда»). Счётчик отклонений
   обнуляется: дальше считаем только `REJECTED` после `warned_at`.
3. **Бан** — `is_active = false`, отзыв всех refresh-токенов, вход блокируется.
   Причина обязательна. Запись в `audit_log`.
4. **Разбан** — сотрудник может вернуть `is_active = true` (одна кнопка). Бан
   обратим, чтобы исправить ошибочное решение. Запись в `audit_log`.

### Порог и подсчёт

- Порог флага: **3** (фиксирован в коде на уровне константы).
- Счётчик = число жалоб автора, у которых есть переход в `REJECTED`
  (`status_changes.to_status = 'REJECTED'`) с `created_at >`
  `coalesce(users.warned_at, '-infinity')`.
- После предупреждения `warned_at` обновляется → счётчик эффективно обнуляется.

## Изменения данных (минимальные)

- **`users.warned_at TIMESTAMPTZ NULL`** (новая колонка) — когда последний раз
  выносили предупреждение. Для обнуления счётчика и показа статуса «предупреждён».
- **Бан/разбан** переиспользуют существующий `is_active` (+ отзыв токенов при бане).
  Состояние «забанен» для жителя = `is_active = false` при `email_verified = true`
  и роли `RESIDENT`.
- **Новые значения `AuditAction`:** `RESIDENT_WARNED`, `RESIDENT_BANNED`,
  `RESIDENT_UNBANNED`. Причина действия пишется в `audit_log.metadata`.
- **Новый `notifications.kind = 'MODERATION_WARNING'`** для уведомления-предупреждения
  жителю. Привязка к жалобе-нарушению через `complaint_id`. Требуется мини-миграция:
  расширить оба CHECK-констрейнта (`notifications_kind_check` и
  `notifications_target_check`), чтобы новый kind допускался и требовал `complaint_id`.

## API (backend)

Под существующим админским неймспейсом, доступ — роли `ADMIN` и `OPERATOR`:

- `POST /auth/admin/residents/{id}/warn` — тело `{ reason, complaintId }`. Шлёт
  уведомление жителю, ставит `warned_at = now`, пишет `RESIDENT_WARNED` в аудит.
- `POST /auth/admin/residents/{id}/ban` — тело `{ reason, complaintId? }`. Ставит
  `is_active = false`, отзывает refresh-токены, пишет `RESIDENT_BANNED`.
- `POST /auth/admin/residents/{id}/unban` — ставит `is_active = true`, пишет
  `RESIDENT_UNBANNED`.

Все три:
- проверяют, что цель — `RESIDENT` (иначе `400/403`; сотрудников модерируем через
  freeze);
- требуют непустую `reason`;
- логируют actor, target, ip, user-agent, reason.

**Сводка модерации для UI.** Деталь жалобы в админке обогащается блоком об авторе:
`{ rejectedCountSinceWarning, isWarned, isBanned }`. Реализуется расширением ответа
детали жалобы (без отдельного запроса — данные нужны ровно там, где показываются
кнопки модерации).

## Веб-админка (UI)

Раздел «Жалобы» → деталь жалобы:

- Рядом с автором — бейдж «⚠ N отклонённых» (если `N ≥ 3` — выделен как флаг
  «на проверку») и метка «предупреждён», если `isWarned`.
- Кнопки **«Предупредить»** и **«Забанить»** с модалкой ввода обязательной причины.
  Для забаненного автора — кнопка **«Разбанить»**.
- Доступ к кнопкам — роли `ADMIN` и `OPERATOR`.
- Отдельной страницы модерации нет.

## Справедливость и безопасность

- Модерация применима только к `RESIDENT`.
- Авто-флаг **не наказывает** — только подсветка; любое действие выполняет человек.
- Причина обязательна и сохраняется в аудит (доказуемость, обжалуемость).
- Бан обратим (разбан) — ошибочное решение можно отменить.
- `DUPLICATE` не учитывается в счётчике — добросовестные повторы не наказываются.
- Все действия (warn/ban/unban) пишутся в `audit_log` с actor/target/ip/reason.

## Краевые случаи

- Модерация не-резидента → ошибка (используйте freeze для сотрудников).
- Пустая причина → `400`.
- Бан уже забаненного / разбан активного → идемпотентно или `409` (выбрать при
  реализации; предпочтительно идемпотентно с понятным ответом).
- Забаненный житель не может войти (уже покрыто проверкой `!isActive`); открытые
  сессии гасятся отзывом refresh-токенов.
- Предупреждение жителю без активной жалобы-нарушения: `complaintId` обязателен в
  warn, т.к. уведомление привязано к конкретной жалобе.

## Тестирование

- Repository/service: подсчёт `REJECTED`-жалоб с учётом `warned_at`; `DUPLICATE`
  не считается; обнуление после предупреждения.
- Warn: ставит `warned_at`, шлёт уведомление нужного kind, пишет аудит.
- Ban: `is_active=false` + отзыв токенов + аудит; вход после бана отклоняется.
- Unban: возвращает доступ + аудит.
- Guard: `OPERATOR` и `ADMIN` — можно; `RESIDENT` — `403`; цель-сотрудник — ошибка.
- Пустая причина → `400`.
- Миграция CHECK-констрейнтов: вставка уведомления `MODERATION_WARNING` с
  `complaint_id` проходит, без — падает.
