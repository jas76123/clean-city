# Демо-сид для аналитики: заполнение «Медианы» и «Соблюдения норматива, %»

Дата: 2026-05-29

## Проблема

На странице «Аналитика» web-admin столбцы **«Медиана»** и **«Соблюдение норматива, %»**
почти везде показывают «—» (пусто). Это касается таблицы «Категории жалоб»
(`AnalyticsPage.tsx`) и таблицы по районам (`EquityTable.tsx`).

Причина — не в коде аналитики, а в бедности dev-данных. Обе метрики считаются
в `AnalyticsRepository.computeResolutionMetrics` **только по жалобам со статусом
`RESOLVED` и заполненным `resolved_at`**, сгруппированным по категории / по району.
Текущий dev-сид (`backend/src/main/resources/db/seed-dev/V99__seed_dev.sql`)
создаёт 50 жалоб, из которых резолвится лишь каждая 7-я (`i % 7 == 0`) — около
7 решённых жалоб, размазанных по 18 категориям и 4 районам. У большинства групп
ноль решённых → `medianResolutionHours = null`, `slaCompliancePct = null` → «—».

## Цель

Добавить в БД набор `RESOLVED`-жалоб так, чтобы:
1. У каждой из 18 категорий была непустая, осмысленная медиана и SLA-процент.
2. У каждого из 4 районов медиана и SLA в `EquityTable` были непустыми.
3. «Соблюдение норматива, %» показывало **реалистичный разноцветный микс**:
   часть категорий зелёные (≥80%), часть жёлтые (60–79%), часть красные (<60%).
4. Текущие тестовые данные (50 жалоб из V99) **не затирались** и не требовался
   wipe / пересоздание БД.

Метрики аналитики и их расчёт остаются без изменений — правим только данные.

## Подход

Отдельный top-up SQL-скрипт + тонкий bash-раннер в `ops/`, по образцу
существующих `ops/trigger-*.sh`. Скрипт вставляет данные напрямую в живой
Docker-Postgres, что даёт полный контроль над `created_at`/`resolved_at`
(а значит над медианой и SLA) — чего нельзя достичь через HTTP-API, где
`resolved_at` всегда равен «сейчас».

### Файлы

- `ops/seed-analytics-demo.sql` — вся логика вставки/отката (PL/pgSQL `DO`-блок).
- `ops/seed-analytics-demo.sh` — раннер: читает `POSTGRES_USER`/`POSTGRES_DB`
  из `.env` (как другие ops-скрипты), коннектится к сервису `db` через
  `docker compose exec -T db psql …`. Поддерживает `--reset`.

### Данные

- **18 категорий × 5 решённых жалоб = 90 жалоб.** ≥3 точек на категорию →
  медиана осмысленна.
- Авторы — существующие резиденты `resident1..5@cleancity.dev` (берём их id;
  при отсутствии — любые пользователи с ролью `RESIDENT`).
- `created_at` разбросан по последним ~25 дням, `resolved_at = created_at +
  время_решения` и всегда `≤ now`. Данные видны в периодах «Месяц» и шире.
- Все 4 района Сочи (`Центральный`, `Адлерский`, `Хостинский`, `Лазаревский`)
  получают решённые жалобы.

### Инженерия SLA-микса

Пороги норматива (из `CategorySla.hoursFor`): **24 ч** для GARBAGE, ECOLOGY,
SAFETY, LIGHTING, SEWAGE, WATER_SUPPLY, ELECTRICITY; **120 ч** для остальных 11.

Категории делятся на 3 тира по доле «в норме» из 5 жалоб:

| Тир     | В норме | SLA % | Цвет на дашборде | Кол-во категорий |
|---------|---------|-------|------------------|------------------|
| Зелёный | 5/5     | 100%  | зелёный (≥80)    | 6                |
| Жёлтый  | 3/5     | 60%   | жёлтый (60–79)   | 6                |
| Красный | 2/5     | 40%   | красный (<60)    | 6                |

Время решения задаётся относительно порога категории:
- «в норме»: доля порога, варьируется (≈0.4–0.8× порога) → разная медиана;
- «просрочка»: ≈1.3–2.0× порога.

Это даёт и разные медианы между категориями, и разноцветный столбец SLA.
Назначение района подбирается так, чтобы SLA-проценты районов в `EquityTable`
тоже различались (не были все одинаковыми), а не строго совпадали.

### Идемпотентность и безопасность

- Все демо-жалобы помечаются распознаваемым маркером `address = 'SLA-DEMO'`.
- Гард перед вставкой: если демо-жалобы уже есть → `RAISE NOTICE` и выход
  (повторный запуск — no-op, дублей не создаёт).
- DEV-only: запускается вручную против локального Docker-Postgres; это
  `ops/`-скрипт, **не** Flyway-миграция, поэтому прод-классpath не затрагивается.
- Откат: `./ops/seed-analytics-demo.sh --reset` →
  `DELETE FROM complaints WHERE address = 'SLA-DEMO'`.

### Голоса / прочая аналитика

Голоса (`votes`) и прочие срезы (votesImpact, reopen) — вне scope: целевые
две метрики их не используют (YAGNI).

## Запуск

```bash
./ops/seed-analytics-demo.sh          # вставить демо-данные
./ops/seed-analytics-demo.sh --reset  # удалить демо-данные
```

## Проверка

1. Запустить скрипт, открыть web-admin → «Аналитика» (период «Месяц»).
2. В таблице «Категории жалоб» столбцы «Медиана» и «Соблюдение норматива, %»
   заполнены и разноцветны (есть зелёные, жёлтые, красные строки).
3. Таблица по районам (`EquityTable`) не пустая, медиана/SLA заданы.
4. Опционально: `curl` к `/analytics/by-category` и `/analytics/by-district` —
   поля `medianResolutionHours` и `slaCompliancePct` ненулевые.
5. `--reset` возвращает дашборд в исходное состояние.
