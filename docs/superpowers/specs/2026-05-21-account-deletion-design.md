## Раздел B — Backend: удаление аккаунта (soft-delete)

### Эндпоинт

`DELETE /auth/me` — внутри существующего `authenticate { }`-блока в
`AuthRoutes.kt` (рядом с `/sessions`, `/2fa`). Путь консистентен с остальными
auth-роутами.

**Доступ:** только роль `RESIDENT`.

- `ADMIN` / `OPERATOR` / `INSPECTOR` → `403 Forbidden` с сообщением
  «Сотрудники удаляются администратором».
- Причина: сотрудники управляются через веб-админку; ограничение также снимает
  риск удаления последнего активного администратора.

**Ответы:**

| Код | Условие |
|-----|---------|
| `204 No Content` | Успешное удаление |
| `401 Unauthorized` | Запрос без валидного JWT |
| `403 Forbidden` | Роль не `RESIDENT` |

### Логика

- **`UserRepository.softDeleteAndAnonymize(userId: Long)`** — в одной транзакции:
  - `is_active = false`
  - `email = 'deleted_<id>@cleancity.local'`
  - `password_hash = ''` (пустая строка)
  - `full_name = NULL`
  - **Отклонение от первоначального замысла:** колонка `password_hash` в схеме
    `NOT NULL` (`database/tables/Users.kt`). Перевод её в nullable — это
    Flyway-миграция плюс правки во всей цепочке логина
    (`UserRow.passwordHash: String`, `PasswordHasher.verify`). За 7 дней до
    защиты это лишний риск. Пустая строка даёт тот же эффект: ни один пароль не
    верифицируется против пустого хеша, а смена email + `is_active=false` и так
    делают вход невозможным.
- **`AuthService.deleteOwnAccount(userId: Long, ip: String?, userAgent: String?)`:**
  1. Анонимизация пользователя (`softDeleteAndAnonymize`).
  2. Отзыв всех refresh-токенов пользователя через существующий
     `TokenRepository.revokeAllUserRefreshTokens(userId)`.
  3. Запись в `audit_log` новым событием `AuditAction.ACCOUNT_DELETED` для
     бумажного следа по 152-ФЗ.

### Жалобы удалённого пользователя

Жалобы **остаются** в системе (прозрачность — `SPEC.md:657`), но автор скрыт.
Имя автора подменяется на уровне `ComplaintRepository.toComplaintRow()`: запрос
жалоб делает `LEFT JOIN Users`, поэтому в строке доступен `Users.isActive` —
если автор `is_active = false`, отдаём `authorName = "Удалённый пользователь"`
вместо `full_name` (который у удалённого уже `NULL`). Это покрывает и ленту, и
детальный экран. Мобильный клиент изменений не требует — он показывает
`authorName` как есть (фолбэк `?: "Аноним"` остаётся для пользователей без
имени).

### Нюанс JWT

Access-токен stateless — серверно отзываются только refresh-токены. До истечения
TTL access-токен формально валиден. Для MVP приемлемо: мобильный клиент сразу
делает локальный teardown сессии (см. Раздел C).

### SPEC

Добавить строку `DELETE /auth/me` в таблицу эндпоинтов `docs/SPEC.md` §4.1:

> `DELETE` | `/auth/me` | Резидент | Удаление собственного аккаунта: soft-delete
> + анонимизация (`is_active=false`, `email='deleted_<id>@cleancity.local'`,
> `password_hash=''`, `full_name=NULL`), отзыв всех refresh-токенов. Жалобы
> остаются, автор скрыт. Для не-резидентов — 403.

## Раздел C — Mobile: удаление аккаунта

### Сетевой слой

- **`AuthApiContract` / `AuthApi`** — добавить `suspend fun deleteAccount()`,
  реализация: `client.delete("/auth/me")`.
- **`AuthRepository.deleteAccount(): Result<Unit>`** — `runCatching`:
  1. Вызвать `authApi.deleteAccount()`.
  2. При успехе — тот же teardown, что в `logout()`: очистка локального
     storage + `BearerAuthProvider.clearToken()` (обязательно — иначе тихая
     подмена пользователя при следующем логине), перевод `AuthState` →
     `Anonymous`.

### ViewModel

- **`ProfileScreenModel.deleteAccount()`** — вызывает `authRepo.deleteAccount()`;
  при ошибке выставляет состояние/сигнал для показа snackbar; при успехе
  ничего дополнительно делать не нужно — смена `AuthState` переключит root.

### UI — `ProfileScreen.kt`

- Новый пункт меню **«Удалить профиль»** — красный (как «Выйти»), расположен
  под пунктом «Выйти».
- Тап → `AlertDialog`:
  - Заголовок: «Удалить профиль?»
  - Текст: «Действие необратимо. Ваши жалобы останутся в системе, но без
    указания автора.»
  - Кнопки: «Отмена» / «Удалить» (красная, деструктивная).
- При подтверждении → `model.deleteAccount()`.
- На время запроса — индикатор/блокировка кнопки; при ошибке — snackbar
  (хост уже есть в `ProfileScreen`).
- При успехе `App.kt` наблюдает `AuthState` и сам переключает root на гостевой
  экран — отдельной навигации не требуется.

### Тесты

- **Backend** — роут-тест `DELETE /auth/me`:
  - `401` для гостя (без JWT);
  - `403` для не-резидента;
  - `204` для резидента + проверка: email анонимизирован, `password_hash` снят,
    `is_active=false`, refresh-токены отозваны.
- **Mobile** — `ProfileScreenModelTest` (новый файл): успешное удаление и
  ошибка удаления.

## Вне scope

- Админский `DELETE /auth/admin/users/{id}` из `SPEC.md` §4 — отдельная задача
  для веб-админки, в этой работе не реализуется.
- Период «отложенного удаления» / grace period — удаление немедленное.
- Экспорт персональных данных перед удалением — не требуется для MVP.

## Критерий готовности

1. В профиле нет пункта «Мои жалобы»; файлы `mycomplaints/*` удалены; проект
   собирается.
2. Житель может удалить аккаунт из профиля через диалог подтверждения; после
   удаления он на гостевом экране, повторный вход под старым email невозможен.
3. Жалоба удалённого пользователя видна в ленте с автором «Удалённый
   пользователь».
4. `DELETE /auth/me` возвращает 403 для сотрудников.
5. Все тесты (backend + mobile) зелёные.
