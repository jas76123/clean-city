## 1. Проверка polling end-to-end

### Проблема

Polling-канал ни разу не проверялся на живом устройстве: уведомления не приходили,
потому что нет дашборда, способного сменить статус жалобы. Бэкенд-логика создания
уведомления при смене статуса покрыта тестом `ComplaintStatusNotificationTest`, но
мобильный polling-цикл (опрос `unread-count`, отображение, снятие unread) — нет.

### Факты архитектуры

- Триггер уведомления — `PATCH /complaints/{id}/status`; требует роль
  `ADMIN`/`OPERATOR`/`INSPECTOR` (`ComplaintService.changeStatus`, гард на строке 223).
- В dev-сидке (`backend/.../db/seed-dev/V99__seed_dev.sql`) есть готовый админ:
  `admin@cleancity.dev` / `Admin12345!`, роль `ADMIN`, 2FA выключена — admin-JWT
  получается через обычный `POST /auth/login`, дашборд не нужен.
- `UnreadCountStore` (мобильный, Koin singleton) опрашивает `GET /notifications/unread-count`
  раз в 30с. Список `GET /notifications?limit=50` грузится при открытии экрана «Уведомления».
- Реальное устройство достукивается до локального backend через `adb reverse tcp:8081`.

### Решение — подход A

Артефакт: `ops/trigger-status-change.sh` — bash-скрипт, который:

1. Логинится `POST /auth/login` как `admin@cleancity.dev` / `Admin12345!`, извлекает
   access-token из ответа.
2. Принимает аргументы `COMPLAINT_ID`, `TO_STATUS`, `COMMENT`; шлёт
   `PATCH /complaints/{COMPLAINT_ID}/status` с телом `ChangeStatusRequest`
   (`toStatus`, `comment`, опционально `duplicateOfId`).
3. Печатает HTTP-статус и тело ответа (новый статус жалобы) для подтверждения.

Скрипт переиспользуемый — он же будет референсом для чекпоинта Day 16.
Базовый URL backend — параметр с дефолтом `http://localhost:8081`.

### Процедура ручного прогона (Samsung A33 5G)

1. Backend поднят локально; на устройстве выполнен `adb reverse tcp:8081`.
2. На телефоне: логин жителем → создать жалобу → запомнить её id.
3. С Mac: `./ops/trigger-status-change.sh <id> IN_PROGRESS "Приняли в работу"`.
4. На телефоне ожидаемо: бейдж на колокольчике появляется ≤30с (поллинг
   `unread-count`); экран «Уведомления» показывает запись с unread-меткой; тап по ней →
   детали жалобы, unread снят.
5. Повторить со статусом `REJECTED` — проверить отображение блока комментария
   администрации в деталях закрытой жалобы.

### Критерий готовности

Оба прогона (`IN_PROGRESS`, `REJECTED`) проходят: бейдж обновился, уведомление
появилось с unread-меткой, тап открыл детали и снял unread.

## 2. Аудит интеграции фронт↔бэк

### Находки

- `API_BASE_URL` — единственное build-config значение, читается из
  `secrets.properties` либо переменной окружения (`composeApp/build.gradle.kts`,
  `buildConfigField` в `defaultConfig`). **Одно значение на debug и release** —
  per-build-type разделения нет.
- `usesCleartextTraffic="true"` в `AndroidManifest.xml` — действует на все сборки.
- Backend ещё не задеплоен (деплой — Day 18). Полноценная интеграция против
  задеплоенного backend объективно невозможна до Day 18.

### Принятые решения

- **Per-build-type split для `API_BASE_URL` не делаем** (YAGNI). Перед release-сборкой
  значение `API_BASE_URL` в secrets меняется вручную на боевой HTTPS-URL. Этот шаг
  фиксируется отдельным пунктом в Day 18-плейбуке, чтобы не забыть.
- `usesCleartextTraffic="true"` оставляем — он нужен для локального HTTP-доступа через
  `adb reverse`. Ужесточение (удаление флага либо сужение network-security-config до
  конкретного хоста) выполняется на Day 18, когда backend будет доступен по HTTPS.
- «Настоящая» интеграция мобильного приложения против задеплоенного backend честно
  переносится на Day 18.

### Работа в Day 14

Зафиксировать находки и решения выше в `docs/PLAN.md` и в Day 18-плейбуке. Кода эта
часть не меняет — это аудит и документирование.
